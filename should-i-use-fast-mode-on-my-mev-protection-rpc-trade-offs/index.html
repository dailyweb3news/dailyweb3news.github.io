Should I use fast mode on my MEV protection RPC? Trade-offs

Enable fast mode on Flashbots Protect when getting a transaction included quickly matters more than maximizing its refund or limiting who sees it; keep…

The Onchain Brief EditorsNov 21, 2026 · 04:07 UTC4 min read

Enable fast mode on Flashbots Protect when getting a transaction included quickly matters more than maximizing its refund or limiting who sees it; keep the default endpoint for routine swaps. Fast mode sends the pending transaction to all builders registered with Flashbots, which increases the chance that the builder winning a slot through MEV-Boost has it in time, while giving the validator a larger share of the backrun value.

Fast mode widens builder reach and reduces your refund

The default Protect endpoint sends a transaction to fewer builders, while fast mode sends it to every builder registered with Flashbots. More builders that may win a block can consider including it, so fast mode raises the odds of timely inclusion; it cannot guarantee that the transaction lands in the next block.

This broader reach comes with a privacy trade-off: each additional builder receives the pending transaction before inclusion. Every one is another party you trust not to leak it. Read the registered builder list before enabling fast mode, and weigh that wider exposure against the value of quicker inclusion.

Fast mode also changes how much backrun value returns to you. The validator receives a larger share of the MEV-Share backrun payment, so less of that value comes back as your refund. A refund percentage you set does not remove this trade-off: the validator's share is part of the value available to return to you.

For a DeFi user weighing the settings while using flashbots.app, the practical choice is whether a particular transaction needs the extra builder reach enough to accept the smaller refund. That is the same trade-off behind Flashbots: broader access to potential block builders may help a time-sensitive transaction, while the default is a better fit when speed is less urgent.

Use fast mode when a delay could cost more than the refund

Choose the endpoint by asking what a missed block would cost you. Fast mode fits a transaction whose value falls quickly with delay; the default fits one that can wait without a meaningful penalty.

Say you need to top up collateral while a lending position is close to liquidation. A delay could leave the position exposed, so broader builder reach may be worth accepting a smaller MEV-Share refund and trusting more builders with the transaction. In that case, choose fast mode.

Now take the same wallet making a routine token swap, with no deadline or liquidation risk. A modest delay is unlikely to change the outcome, so the extra builder exposure and smaller refund have little upside. Keep the default endpoint.

In both cases, inclusion still depends on a builder winning the slot through MEV-Boost and receiving the transaction in time. Fast mode improves the chance that a winning builder has it; it does not control which builder wins or promise inclusion. Use it to improve the odds when the cost of waiting is high.

A simple rule is to compare the cost of delay with the refund you give up and the additional builders you trust. If delay could cause liquidation or another material loss, use fast mode. If the transaction is routine and can wait, use the default.

Related

What is the Flashbots Protect fast mode URL?

The fast mode endpoint is rpc.flashbots.net/fast. It sends the transaction to all builders registered with Flashbots.

Does fast mode lower my MEV-Share refund?

It can: fast mode gives the validator a larger share of the backrun payment, leaving less value to return to you.

Can fast mode be combined with custom builder settings?

Fast mode's defining behavior is sending to all registered builders. Treat a custom builder list as a separate control, and confirm the behavior of your specific RPC configuration before relying on the two settings together.
